# PlanProof Engineering Build Plan

**Status:** implementation blueprint
**Product:** PlanProof — verification infrastructure for AI-generated engineering plans
**Audience:** builders, reviewers, and AI-agent engineering interviewers
**Primary target:** Software Developer, AI Agents (Enterprise Planning), ProdE

---

## 1. The project we are building

PlanProof is **not** a coding agent and it is **not** a chat-with-your-codebase wrapper.

It receives a repository snapshot, a change request, and a candidate engineering plan. It converts the plan into explicit claims (proof obligations), gathers evidence using controlled tools, and returns one of four meaningful outcomes per claim:

| Outcome | Meaning |
| --- | --- |
| `VERIFIED` | Available evidence satisfies the declared verification policy. |
| `DISPROVED` | Reproducible counter-evidence contradicts the claim. |
| `INCONCLUSIVE` | Evidence is insufficient or conflicting. This is an honest result. |
| `HUMAN_REQUIRED` | The answer needs business/product/operational authority that code cannot provide. |

The one-sentence product story is:

> **Engineering plans are hypotheses. PlanProof tests them before agents build them.**

The central demo must show a plausible but incorrect plan assumption being disproved with exact repository evidence, and an unknowable assumption being left unknown. That demonstrates engineering judgment better than an impressive generated paragraph.

---

## 2. Why this project fits the ProdE role

The role asks for production AI agents for enterprise planning, reliable tool use, durable state, retrieval, evaluations, MongoDB, and judgment about when *not* to use agents. PlanProof makes each capability inspectable in code.

| Job requirement | PlanProof proof in the repository |
| --- | --- |
| Production AI agents | A durable, bounded verification workflow with typed state and terminal states. |
| Planning loops | Claim → evidence action → validator → state transition → stop/escalate. |
| Tool use | Repository search, symbol lookup, dependency graph, schema inspection, test discovery, bounded probes. |
| Memory | MongoDB stores immutable snapshots, runs, checkpoints, evidence, decisions, and versions. |
| Human-in-the-loop | A run pauses for an authoritative question, persists it, and resumes safely. |
| Retrieval | Lexical, symbol/dependency, and semantic retrieval merged with deterministic ranking. |
| Strong Python | FastAPI, Pydantic, async I/O, workers, policies, tests, typed interfaces. |
| Reliability/cost | Timeouts, idempotency, budgets, retries, provider fallback, tracing. |
| MongoDB | Deliberate document schemas, compound indexes, TTL retention, Atlas Search/Vector Search filters. |
| Evaluation | Versioned planted-failure scenarios with accuracy, abstention, cost, and latency metrics. |

### Deliberate non-decisions

These are important interview answers, not missing features:

- **No multi-agent swarm for MVP.** One stateful orchestrator is easier to audit, cheaper, and less likely to fabricate consensus. Add a separate worker only when it gathers a genuinely different signal, such as an isolated executable probe.
- **No arbitrary shell given to the model.** Repository contents and model outputs are untrusted. The model can request strict, least-privilege tools; server policy decides whether to execute them.
- **No model-owned status or citations.** The model may propose an interpretation and cite server-issued evidence IDs. Policy code alone commits `VERIFIED`, `DISPROVED`, or escalation.
- **No fake metrics.** UI quality numbers remain hidden until generated by the real evaluator and committed with reproducible configuration.
- **No private GitHub access in P0.** Build the seeded demo and public-repo mode first. Add a read-only GitHub App only after the core loop is reliable.

## 4. Architecture: authority, data flow, and trust boundaries

```text
Browser (Next.js)
   │ HTTPS + SSE only
   ▼
FastAPI API ──────────────── MongoDB Atlas
   │ create jobs / read projections       │ source of truth
   ▼                                      │
Redis queue ◄────────────── Worker ───────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
        Repo/index tools       Model gateway            Bounded probe runner
        deterministic          OpenRouter/AIMLAPI        isolated, allowlisted
```

### Authority rules

| Component | Allowed to do | Must never do |
| --- | --- | --- |
| Browser | Collect input, show projections, submit human answers. | Hold provider keys, decide statuses, access cloned repository. |
| LLM | Extract claims, choose from allowed next actions, interpret evidence, draft amendments. | Write DB state directly, invent evidence IDs, execute shell, override budgets. |
| Tool layer | Produce typed, bounded facts and artifacts. | Return data outside snapshot/path policy. |
| Policy layer | Validate evidence, enforce budgets, make mechanical state transitions. | Guess business rules or use model confidence as proof. |
| Human | Resolve authoritative business/product/operational unknowns. | Retroactively alter immutable evidence. |

### Snapshot rule

Every run references exactly one immutable snapshot:

```text
repository URL + requested ref + resolved commit SHA + content hash
+ parser version + index version + embedding model/version
```

Evidence without a `snapshot_id`, content hash, source tool run, and bounded source location is invalid. A newer branch head never changes evidence attached to an old run.

## 5. Technology decisions

| Concern | Decision | Why |
| --- | --- | --- |
| Frontend | Next.js 16 App Router + TypeScript | Existing UI already uses it. Keep server/client boundaries explicit and use SSE for run progress. |
| API | FastAPI + Pydantic v2 | Typed contracts, OpenAPI, async I/O, excellent Python ergonomics. |
| Durable workflow | LangGraph | Justified by checkpointing, bounded graph loops, and interrupt/resume—not by trend-following. |
| Primary database | MongoDB Atlas + PyMongo Async | Flexible versioned artifacts with explicit schema validation, plus operational and vector search workload. |
| Queue | Redis + Dramatiq (or Celery only if operational needs justify it) | Long indexing/verification must not run in API processes. Start with a small, understandable worker model. |
| Code analysis | `tree-sitter` + language-specific lightweight extractors | Parse Python and TypeScript/JavaScript first; never claim all-language support. |
| Exact search | `ripgrep` against a controlled snapshot workspace, with persisted metadata | Exact identifiers, paths, and error strings matter in code. |
| Semantic retrieval | MongoDB Atlas Vector Search, snapshot-scoped filters | Complement exact search; never replace it. |
| LLM client | Internal provider-neutral gateway using OpenAI-compatible SDK | OpenRouter and AIMLAPI can be configured behind one typed interface. |
| Observability | OpenTelemetry + structured JSON logs | Trace API/job/model/tool spans across the workflow. |
| E2E testing | Playwright | Validates the actual seeded demo, evidence clicks, pause/resume, and export. |

### Official documentation used for these choices

- [LangGraph interrupts and durable persistence](https://langchain-ai.github.io/langgraph/concepts/breakpoints/) — persisted interrupts support human approval/resume.
- [LangGraph persistence concepts](https://langchain-ai.github.io/langgraphjs/how-tos/cross-thread-persistence-functional/) — distinguish thread checkpoints from application-owned long-term state.
- [MongoDB Vector Search overview](https://www.mongodb.com/docs/vector-search/) and [PyMongo indexes](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/indexes/) — vector indexes are separate and metadata filters must be indexed.
- [FastAPI background-task caveat](https://fastapi.tiangolo.com/tutorial/background-tasks/) — heavy work belongs in separate worker processes/queue, not request handling.
- [OpenTelemetry Python](https://opentelemetry.io/docs/languages/python/) — traces and metrics are stable APIs; logs need more care.
- [OpenRouter quickstart](https://openrouter.ai/docs/quickstart) and [AIMLAPI OpenAI SDK configuration](https://docs.aimlapi.com/faq/openai-sdk-doesnt-work) — both support an OpenAI-compatible client with provider-specific base URL.
- Local Next.js 16 docs at `node_modules/next/dist/docs/01-app/` — App Router routing, layouts, route handlers, and project structure must be consulted before frontend implementation changes.

## 6. MongoDB data model and indexes

MongoDB is the source of truth for product state, auditability, and retrieval metadata. Do not use it as an unstructured dumping ground: every collection has a Pydantic model, validator, ownership rule, and query-driven indexes.

### Collections

| Collection | Purpose | Key fields |
| --- | --- | --- |
| `projects` | User/project container | `_id`, owner/session, name, repository source, timestamps |
| `repository_snapshots` | Immutable code snapshot identity | project ID, resolved SHA, root hash, parser/index/embedding versions, state |
| `repository_files` | File metadata, hashes, language, ignore reason | snapshot ID, path, content hash, size, language |
| `code_symbols` | Symbol and reference graph | snapshot ID, qualified name, kind, file, range, outgoing/incoming refs |
| `code_chunks` | Retrieval chunks | snapshot ID, path, symbol, text/hash, embedding, metadata |
| `plan_versions` | Immutable candidate plan history | project ID, version, change request, plan text, parent version |
| `verification_runs` | Durable run projection and budgets | snapshot ID, plan version ID, status, counters, timestamps |
| `proof_obligations` | Server-owned claim state | run ID, statement, category, criticality, methods, status, policy result |
| `evidence` | Source-grounded evidence | snapshot ID, tool run ID, content hash, source path/range, artifact hash |
| `tool_runs` | Audit of every tool invocation | run ID, input hash, output summary, timing, status, error class |
| `model_calls` | Provider/model usage and cost | run ID, provider, model, request hash, tokens, latency, estimated cost |
| `human_questions` | Interrupt state and answer provenance | obligation ID, question, authority needed, answer, actor, timestamps |
| `events` | Append-only UI/event feed | run ID, sequence, event type, safe summary, trace ID |
| `eval_runs` | Evaluation configuration and measured results | case version, build SHA, model/index config, metric output |

### Required operational indexes

```text
repository_snapshots: { project_id: 1, resolved_commit_sha: 1 } unique
repository_files:     { snapshot_id: 1, path: 1 } unique
code_symbols:         { snapshot_id: 1, qualified_name: 1 }
code_chunks:          { snapshot_id: 1, path: 1, symbol: 1 }
plan_versions:        { project_id: 1, version: 1 } unique
verification_runs:    { project_id: 1, created_at: -1 }
verification_runs:    { status: 1, updated_at: 1 }
proof_obligations:    { run_id: 1, status: 1, criticality: 1 }
evidence:             { snapshot_id: 1, source_tool_run_id: 1 }
tool_runs:            { run_id: 1, started_at: 1 }
events:               { run_id: 1, sequence: 1 } unique
human_questions:      { status: 1, updated_at: 1 }
```

Use TTL indexes only for non-audit data such as temporary clone leases, transient event caches, and expired anonymous sessions. Do **not** TTL-delete reports, evidence, or human decisions without an explicit product retention policy.

### Vector/search indexes

Create a versioned Atlas Vector Search index on `code_chunks.embedding` and filter fields for at least `snapshot_id`, `language`, `path`, and `chunk_type`. All semantic queries must include `snapshot_id` as a pre-filter. Exact text search is separate; semantic score alone cannot establish code facts.

## 8. Repository ingestion and code intelligence pipeline

### P0 input policy

- Seeded demo repository always available without credentials.
- Public GitHub repositories only, HTTPS URL allowlist, optional branch/tag.
- Resolve ref to an immutable commit SHA before reading/indexing.
- Enforce repository size, file count, clone time, per-file size, and total-text limits.
- Exclude binaries, vendored code, generated directories, dependency directories, lockfile blobs, and configured ignores.
- Support Python and TypeScript/JavaScript only for P0.

### Indexing stages

1. Validate repository URL and requested ref.
2. Clone to a worker-owned temporary directory with a time/size budget.
3. Resolve commit SHA and calculate repository/file content hashes.
4. Apply deterministic ignore policy; record ignored files and reasons.
5. Detect language and parse supported source files.
6. Extract symbols, imports, exports, references, schema/OpenAPI files, and test candidates.
7. Create AST-aware chunks: module overview, class/function body, schema/API section, test section.
8. Persist files/symbols/chunks in MongoDB.
9. Compute embeddings in bounded batches; persist embedding version.
10. Build/check search indexes; mark snapshot `READY` only when required stages succeed.

Indexing must be idempotent on `(repository source, resolved SHA, parser version, index version, embedding version)`. Repeated requests should attach to existing successful work or safely retry a failed stage.

## 9. Tools: strict interfaces, not unrestricted agent access

Each tool has typed input/output, an execution timeout, maximum result size, snapshot containment checks, and a persisted `tool_run` record.

| Tool | P0? | Policy |
| --- | --- | --- |
| `list_files` | Yes | Prefix/glob only, bounded result count. |
| `search_code_lexical` | Yes | Exact/token search over one snapshot, capped matches/context. |
| `read_file_range` | Yes | Repository-root containment, text-only, bounded lines/bytes. |
| `find_symbol` | Yes | Query persisted symbol index only. |
| `find_references` | Yes | Bounded graph references from persisted graph. |
| `get_dependency_neighbors` | Yes | Direction/depth/result cap required. |
| `inspect_schema` | Yes | Known ORM/SQL/schema/OpenAPI formats only. |
| `inspect_openapi` | P1 | Parse supported OpenAPI version; do not use an LLM to read YAML facts. |
| `test_discovery` | P1 | List test candidates; do not execute arbitrary commands. |
| `test_run` / `sandbox_probe` | P1 | Allowlisted runner/spec only; no network, secret, or host filesystem access. |
| `git_log_path` / `git_blame_range` | P1 | Bounded output tied to snapshot/history policy. |

No tool result is final proof by itself. A deterministic validator or policy rule decides whether the evidence is sufficient for a claim category and criticality.

## 10. Agent workflow

### State machine

```text
CREATED → INDEX_REQUIRED → INDEXING → READY
READY → EXTRACTING_OBLIGATIONS → VERIFYING
VERIFYING → VERIFYING             (more evidence, budget remains)
VERIFYING → HUMAN_WAIT            (authority required)
HUMAN_WAIT → VERIFYING            (persisted answer resumes)
VERIFYING → FINALIZING → COMPLETE
any active state → FAILED          (non-recoverable platform error)
```

### Verification loop per obligation

1. Load one pending obligation and its current evidence set.
2. Apply deterministic short-circuit validators first (symbol existence, unique constraints, schema/API compatibility where supported).
3. If unresolved, ask the model for a **schema-valid next action** chosen from a server allowlist.
4. Execute one tool with strict policy/budget limits.
5. Validate and persist evidence with server-generated IDs.
6. Ask the model for an interpretation proposal that cites only evidence IDs.
7. Policy layer verifies citations, snapshot ownership, evidence requirements, and transition rules.
8. Commit terminal status or loop. On budget exhaustion, return `INCONCLUSIVE` or `HUMAN_REQUIRED`, never artificial confidence.

### Required state fields

```python
run_id, project_id, snapshot_id, plan_version_id, status,
current_obligation_id, completed_obligation_ids,
open_human_question_ids, iteration_count, model_call_count,
tool_call_count, probe_count, retrieved_context_bytes,
prompt_tokens, completion_tokens, estimated_cost_usd,
started_at, updated_at
```

### Starting budgets

Treat these as configuration and evaluate them; do not hard-code business constants in graph nodes.

| Budget | Initial P0 value |
| --- | --- |
| Investigation iterations per obligation | 5 |
| Tool calls per obligation | 8 |
| Model calls per obligation | 3 |
| Retrieved context | 24 KB after tool-result trimming |
| Wall clock per obligation | 90 seconds |
| Sandbox probes per run | 0 in P0; 1 in P1 |
| Run model spend | small configurable ceiling, shown before run starts |

### Human-in-the-loop

A human question is a first-class domain object, not a chat message. Record question wording, why it is needed, requested authority, actor/session, answer, timestamp, and affected obligation. Resume using persisted run/checkpoint data only.

## 11. Retrieval and evidence policy

### Retrieval order

1. **Symbol lookup** for named classes/functions/tables/endpoints.
2. **Lexical retrieval** for exact identifiers, constraints, strings, and routes.
3. **Dependency graph** for bounded caller/callee or import impact.
4. **Semantic retrieval** for concept synonyms and likely relevant modules.
5. **File reads** only for bounded candidates selected by the prior stages.

Merge results deterministically. Give exact source matches and symbol identity higher priority than embedding similarity. Require snapshot filtering everywhere.

### Evidence acceptance rules

- A model may not create `evidence_id`, file paths, line ranges, snapshot IDs, hashes, or tool runs.
- A `VERIFIED` critical claim requires policy-defined evidence types, not merely a model explanation.
- A `DISPROVED` claim needs direct counter-evidence or a deterministic validator failure.
- Missing search results are never enough to prove absence unless the index completeness and relevant search scope are established.
- Every report labels the verification scope and method; it does not claim formal proof of arbitrary behavior.

## 12. Provider gateway, cost, and resilience

Implement a small interface such as `ModelGateway.complete(request) -> ModelResult`; graph nodes depend on the interface, never a vendor SDK.

`ModelResult` records provider, model, request/response schema version, latency, token usage, estimated cost, retry count, and safe error class.

### Routing policy

1. Use a pinned configured primary model for structured claim extraction and interpretation.
2. Retry only transient transport/rate-limit failures with exponential backoff + jitter, respecting deadline and cost budget.
3. If primary fails within policy, use a configured fallback through the same schema contract.
4. Never silently switch model on a quality failure. Record every route/fallback in the report and eval configuration.
5. Store keys server-side only: local `.env` ignored; deployed platform secret store in production.

OpenRouter and AIMLAPI both provide OpenAI-compatible endpoints, so they fit one adapter shape. Test both against mocked HTTP responses first, then run a separately budgeted integration smoke test.

## 13. Reliability, security, and operational design

### Failure handling

| Failure | Required response |
| --- | --- |
| Duplicate API request | Idempotency key returns original job/run, not duplicate work. |
| Worker crash | Job lease expires; a worker resumes from persisted state/checkpoint. |
| Provider timeout | Classified failure, bounded retry, then configured fallback or safe `ERROR`/`INCONCLUSIVE`. |
| Tool timeout | Persist failed tool run; allow only a bounded alternative action. |
| Budget exhausted | Terminal `INCONCLUSIVE` or `HUMAN_REQUIRED`. |
| Snapshot mismatch/stale index | Reject evidence; re-index or create a new run. |
| Unsupported repo | Explicit unsupported result; never partial silent indexing. |

### Security baseline

- Treat repository files, READMEs, comments, issues, and model output as untrusted input.
- Do not place raw repository content in system/developer instructions; pass it as clearly labeled untrusted tool output.
- Validate GitHub URLs/hosts; block local file, credentialed, and non-HTTPS repository URLs.
- Enforce path containment with resolved paths; reject traversal and symlink escapes.
- Scan/index only configured text content; redact secret-like data from model context and logs where feasible.
- Give the browser no provider/database/repository credentials.
- Rate-limit public endpoints and apply payload/file/repository limits.
- Use structured allowlisted probe specs; never let an LLM compose arbitrary host shell commands.
- Add adversarial tests for prompt injection in README/code comments, invented citations, malformed JSON, stale snapshot, tool loops, and path traversal.

### Observability

Create a trace for each API request and continue it through queue/job/workflow/tool/model spans. Add structured fields: `run_id`, `snapshot_id`, `obligation_id`, provider/model, tool name, decision/status, latency, token count, and cost estimate. Do not log full repository content, prompts, secrets, or human answers by default.

## 14. The seeded demo repository

Build `demo-repos/payments-platform` as a small multi-module Python + TypeScript repository. It is not fake data: PlanProof must parse and inspect its real files.

### Change request

```text
Add partial refunds while keeping existing full-refund behavior and API compatibility.
```

### Candidate plan

```text
1. Add an optional refund amount to PaymentService.refund().
2. Forward the amount to the payment provider.
3. Reuse the existing refunds table; no migration is needed.
4. Existing idempotency behavior works unchanged.
5. Billing and analytics are unaffected.
6. Preserve the existing public API response.
```

### Required repository truths and results

| Claim | Truth intentionally present in the repository | Expected outcome |
| --- | --- | --- |
| Provider accepts `amount` | Provider adapter already supports an amount parameter. | `VERIFIED` |
| Schema supports multiple refunds | `refunds.payment_id` has a unique constraint. | `DISPROVED` |
| Idempotency works unchanged | Key is based only on payment ID, causing partial-refund collision. | `DISPROVED` |
| Billing is unaffected | Billing logic assumes full capture amount for refund accounting. | `DISPROVED` |
| API can remain compatible | Existing response supports additive field or compatible representation. | `VERIFIED` |
| Mobile impact is known | No mobile repository is connected. | `HUMAN_REQUIRED` |

Write tests inside the demo repository that confirm these truths. The product then verifies a real repository, while expected outcomes remain stable for E2E and evaluator tests.

## 15. Evaluation harness

An agent system cannot improve safely if quality is judged by demo impressions. Build the evaluator alongside the core workflow, not after it.

### Case format

Each case includes:

```text
case ID + version
fixture repository revision
change request + candidate plan
expected obligation categories/criticality
expected status or accepted status set
required evidence source(s)
forbidden false-positive evidence/statuses
human-question expectation
budget and provider/index configuration
```

### P0 scenario groups (minimum 20 cases)

- false database/schema assumption;
- false dependency-impact assumption;
- false idempotency assumption;
- public API compatibility;
- missing repository / unknown cross-service impact;
- stale snapshot;
- empty or malformed plan;
- duplicate obligation extraction;
- provider timeout/fallback;
- malformed model structured output;
- unknown/invented evidence ID;
- prompt injection in README;
- prompt injection in a source comment;
- tool timeout;
- repetitive tool-loop/budget exhaustion;
- path traversal attempt;
- generated/vendor directory ignored;
- conflicting evidence;
- cancellation/retry/idempotency;
- human question and resume after simulated worker restart.

### Metrics

| Metric | Definition |
| --- | --- |
| Critical-assumption recall | Expected critical false/unknown claims surfaced ÷ expected critical claims. |
| Status accuracy | Correct terminal status over labeled obligations. |
| Unsupported-verification rate | `VERIFIED` claims lacking required evidence ÷ all verified claims. Must trend toward zero. |
| Evidence provenance validity | Evidence citations passing snapshot/hash/tool/range policy ÷ all citations. |
| Appropriate escalation rate | Unknown/business-rule cases correctly marked `HUMAN_REQUIRED`/`INCONCLUSIVE`. |
| Retrieval recall@k | Expected source locations found in the top `k` retrieved candidates. |
| P50/P95 latency | Measured by stage and complete run. |
| Cost/run | Provider-recorded or estimated model cost by configuration. |
| Budget-exhaustion safety | Exhausted runs that safely abstain ÷ exhausted runs. |

Commit case definitions and evaluator code. Publish only measured results with the exact Git SHA, model/provider, index version, date, sample count, and limitations.

- Implement lexical search, file reads, symbol lookup, dependency neighbors, schema inspection.
- Add typed tool schemas, result limits, path safety, audit records, evidence creation.
- Build deterministic validators for symbol/file/schema claims.

**Exit:** Tests prove source ranges/hashes are valid and stale or invented evidence cannot be accepted.

### Phase 4 — Model gateway and claim extraction (3–4 days)

- Implement OpenRouter and AIMLAPI adapters behind `ModelGateway`.
- Implement structured extraction with schema validation, retry policy, usage accounting, and fallback tests.
- Create server-side obligation IDs and deterministic dedupe policy.

**Exit:** Invalid model JSON, provider failure, and invented IDs are safely rejected in tests.

### Phase 5 — Durable verification workflow (5–7 days)

- Implement LangGraph state/nodes, persistent checkpoints, budget policy, and terminal transition policy.
- Add action selection, evidence loop, interpretation proposal, and policy gate.
- Emit safe progress events to MongoDB/SSE.

**Exit:** Seeded demo produces at least two `DISPROVED`, two `VERIFIED`, and one `HUMAN_REQUIRED` result using real evidence.

### Phase 6 — Frontend integration (4–6 days)

- Replace static fixture flows with generated client/API calls.
- Implement indexing states, SSE live progress, run report, evidence detail, and export.
- Add loading/error/empty states; do not expose chain-of-thought—show action summaries and tool outcomes.

**Exit:** A fresh browser session can complete the seeded demo without any developer setup.

### Phase 7 — Human pause/resume and plan versions (3–4 days)

- Persist human questions/answers and resume workflow deterministically.
- Add suggested amendment as a non-authoritative draft; accepting it creates a new plan version and marks dependent claims stale.

**Exit:** A simulated API/worker restart during human wait does not lose the run; old plans/evidence stay auditable.

### Phase 8 — Evaluations, security, and operational hardening (5–7 days)

- Build 20+ eval cases and CI smoke subset.
- Add injection, path traversal, stale snapshot, provider/tool failure, cancellation, and loop tests.
- Add OpenTelemetry, structured logging, rate limits, readiness, smoke test, and error reporting.

**Exit:** CI publishes measured eval artifact; no fake quality metric remains in product copy.

### Phase 9 — Production-style deployment and application package (3–5 days)

- Deploy web, API, and worker independently; managed MongoDB/Redis; HTTPS and secret store.
- Publish architecture/security/evaluation docs, README, demo script/video, limitations, and live status.

**Exit:** A reviewer can run the seeded demo in under 90 seconds, inspect evidence, and understand the architecture in under one minute.

## 18. Learning track: learn while building

The goal is not collecting framework knowledge; it is being able to explain each production trade-off with code and a failure case.

### Week 1: production Python and API contracts

- Learn FastAPI dependency injection, Pydantic validation, async boundaries, OpenAPI, health/readiness, exception handling.
- Read: [FastAPI deployment concepts](https://fastapi.tiangolo.com/deployment/concepts/) and [background task caveat](https://fastapi.tiangolo.com/tutorial/background-tasks/).
- Build: API skeleton, domain models, Mongo repositories, health endpoints, pytest suite.

### Week 2: MongoDB and retrieval data pipelines

- Learn document modeling, compound-index design based on query patterns, `explain`, TTL use, Atlas Search vs Vector Search, metadata filtering.
- Read: [MongoDB Vector Search](https://www.mongodb.com/docs/vector-search/), [PyMongo Search](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/atlas-search/), [PyMongo indexes](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/indexes/).
- Build: snapshot/index pipeline and inspect real query plans/index status.

### Week 3: code intelligence and deterministic tool safety

- Learn AST concepts, source ranges, call/import graphs, bounded searches, path containment, parser failures.
- Build: Python/TypeScript symbol extraction and the strict tool layer.
- Demonstrate: a test that rejects an invalid line range and a test that blocks path traversal.

### Week 4: stateful agents and HITL

- Learn structured output validation, graph nodes, checkpoints, interrupts, bounded loops, failure routing.
- Read: [LangGraph interrupt docs](https://langchain-ai.github.io/langgraph/concepts/breakpoints/) and [Thinking in LangGraph](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph).
- Build: one orchestrator with a human pause/resume test. Be able to defend why this is not a multi-agent system.

### Week 5: model reliability and evaluation

- Learn provider abstraction, retries/fallbacks, schema failure handling, evaluation data design, retrieval and abstention metrics.
- Read: [OpenRouter quickstart](https://openrouter.ai/docs/quickstart) and [AIMLAPI supported SDKs](https://docs.aimlapi.com/quickstart/supported-sdks).
- Build: both adapters, provider mocks, and the first 10 labeled eval cases.

### Week 6: observability and deployment

- Learn trace/span design, correlation IDs, redaction, queue semantics, worker restarts, rate limiting, deployments.
- Read: [OpenTelemetry Python](https://opentelemetry.io/docs/languages/python/).
- Build: run/tool/model spans; deploy only after tests and seeded demo are stable.

## 20. Application-ready definition of done

PlanProof is ready to send to ProdE only when all statements below are true:

- A public seeded demo works without GitHub credentials.
- The demo uses a real repository and real tool output, not UI fixtures.
- It reliably disproves at least two critical planning assumptions with file/line/snapshot evidence.
- It verifies at least two supported claims using declared deterministic methods.
- It explicitly raises one human-authority unknown rather than guessing.
- Runs, evidence, questions, tool calls, and plan versions survive worker/API restart.
- The model cannot mutate status or invent valid citations.
- Loops, time, tools, retrieved context, probes, and model spend are bounded.
- OpenRouter and AIMLAPI paths have provider/fallback tests.
- MongoDB contains deliberate schemas and indexes used by real application queries.
- At least 20 versioned evaluation cases exist; UI metrics are generated from those runs.
- Prompt injection, stale snapshot, malformed model JSON, tool timeout, and path traversal tests pass.
- CI is green; secrets are absent from Git; production keys never reach the browser.
- README, architecture, security, evaluation, limitations, and demo video accurately describe the current implementation.

When these are complete, this is no longer “a project with AI API keys.” It is a credible, inspectable AI engineering system: it has durable workflow control, evidence authority, retrieval infrastructure, evaluation discipline, operational failure handling, and clear product judgment.
